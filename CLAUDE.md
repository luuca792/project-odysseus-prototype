# Project Odysseus — Chi hội sinh viên Trà Vinh Management System

This file orients a new Claude Code session picking up this project. Read it before touching code.

## What this project is

A management system for **Chi hội sinh viên Trà Vinh** ("Student Sub-Association of Trà Vinh"), a chapter under **Liên chi hội sinh viên Vĩnh Long**, itself under Hội Sinh Viên Đại học Cần Thơ (Can Tho University's Student Association). It manages students originally from Trà Vinh province who study at Can Tho University.

The project is in the **prototype phase**: building a clickable UI to validate the product idea with stakeholders before any real backend/architecture work begins. There is no backend, no database, no real authentication — see [Prototype scope](#prototype-scope-important) below.

## Repo layout note

This repo (`project-odysseus-prototype`) is the standalone, pushable extraction of the prototype app. It was split out of a larger working directory (`project-odysseus`, not itself a git repo) that also contained the original Word spec, brand resources, and planning docs. Those reference materials were copied into `docs/` here (see the table below) so this repo is self-contained. **The app itself has no dependency on anything outside this repo** — fonts, the CTU logo, and event photos were already self-hosted under `src/assets/` before the split (confirmed by grepping for external/absolute path references — none exist), so nothing needed to be rewired when the paths were flattened out of the old `prototype/` subfolder into this repo's root.

## Prototype scope (important)

This is explicitly **not** a production build. Decisions were made accordingly:

- **No backend, no database.** All data is static/in-memory mock data seeded from `src/mock-data/`.
- **No real authentication.** Login is a "pick a demo account" screen — no passwords, no tokens. Auth state lives only in React context (`AuthContext`) and is lost on page refresh or direct URL navigation (this is expected, not a bug).
- **No real file upload.** Activity images are chosen from a small bundled placeholder gallery (`ImagePicker`); documents are mocked filenames (`DocumentPicker`).
- **No real Word/PDF export.** The Document Generator page shows a live preview and "download" buttons that just toast "not implemented in prototype."
- **CRUD actions do work within a session** — creating an activity, assigning a badge, posting a comment, etc. all update React state and reflect immediately in the UI. None of it persists past a page reload.
- **Profile editing (name/bio/MSSV/major) is display-only** — it updates local state for the session but has no validation or backing logic, per explicit instruction.
- Ambiguous areas from the original spec (quota definition, feedback workflow, forum moderation timing, admin role scope, etc.) are implemented as a reasonable guess **with a visible on-screen disclaimer** so stakeholders react to the assumption directly. See `docs/prototype-specification.md` §7 for the full list.

## Data model (`src/mock-data/`)

- **`types.ts`** — all shared TypeScript interfaces/types. Notably:
  - `Role = 'member' | 'bch' | 'admin'` — exactly 3 functional roles, confirmed by the stakeholder. Do not add more.
  - `BchTitle = 'chi-hoi-truong' | 'chi-hoi-pho' | 'uy-vien-bch'` — a **display-only** label on top of the `bch` role. All three titles have identical permissions in the system; only the label shown in the UI differs. A `User` has an optional `bchTitle` field.
  - `User` also carries `studentId` (MSSV) and `major` (ngành học), both optional strings, sourced from real data.
  - **`User.subAssociationIds: string[]`** — a member can belong to 1+ chi hội (per the "Cách vận hành" update). Admin has `[]`. Currently every real user has exactly one (`['sa-tv']`) since there's still only one real chi hội in `business_data/` — the array shape is structural readiness, not exercised multi-membership; don't fabricate a second chi hội to demo it (confirmed with the user — see Session history #11). `AuthContext` tracks a separate `activeSubAssociationId` (defaults to the user's first membership on login) that all chi-hội-scoped pages read instead of a plural field directly — use `activeSubAssociationId`, not `currentUser.subAssociationIds[0]`, in new page code.
  - **`Permission`** — a fixed string-literal union (23 values) mirroring the spec's "Quyền" list (Tạo tài khoản, Xem hoạt động, Kiểm duyệt bài viết, Quản lý quỹ, etc). This is a system concept per the spec — developer-coded, not user-creatable. See `permissions.ts` below for the editable role→permission mapping.
  - **`Activity.benefits: string[]`** — "Lợi ích tham gia" (e.g. "Điểm rèn luyện", "Đạt tiêu chí Tình nguyện tốt của danh hiệu Sinh viên 5 tốt"), added alongside the pre-existing `date`/`location`/`description`. `ActivityForm` has a repeatable add/remove text-list input for it; `ActivityDetail` renders it as a bulleted "Lợi ích khi tham gia" section.
  - **`Activity.mediaIds` / `documentIds`** replace the old `imageIds` / `documents: {name,size}[]` — both are arrays of `Media` ids resolved via `mock-data/media.ts`, not inline objects.
  - **`Media`** — the generic attachment entity (`kind: 'image' | 'document'`) per the spec's "Tài liệu" entity. Modeled generically (so a Post/Comment could reference the same ids later) but only `Activity` uses it today.
  - **`Post`** — the unified technical entity for both forum posts and feedback ("góp ý"), per the spec's note that these are the same entity distinguished by `postType: 'forum' | 'feedback'`. `Comment[]` always belongs to a `Post` (feedback-type posts just don't show a comment composer in the UI). Status is intentionally a union of two different vocabularies (`'published' | 'hidden'` for forum, `'new' | 'reviewed'` for feedback) rather than one merged enum — confirmed with the user, since the two mean different things.
  - **`Goal`** (Chỉ tiêu) — belongs to one `termOfOffice`, has an `activityIds: string[]` (N activities assigned to it), replacing the old flat `targetActivities`/`completedActivities` count pair. `Quota` page lets BCH create goals and assign/unassign activities to them via a modal.
- **`roleLabels.ts`** — `getUserRoleLabel(user)` is the **single source of truth** for displaying a user's role/title anywhere in the UI. It returns the specific `bchTitle` label for BCH users (falling back to generic "Ban Chấp Hành" if unset) or the plain role label otherwise. **Always use this helper for role display; never hardcode role-label maps in a page component** (this was a real bug fixed during development — see Session history below).
- **`permissions.ts`** — `PERMISSION_LABELS` (Vietnamese display labels for the matrix UI), `ALL_PERMISSIONS`, and `defaultRolePermissions: Record<Role, Permission[]>` — the **seed only**. The live, admin-editable mapping lives in `AppDataContext`'s `rolePermissions` state (see below); don't read `defaultRolePermissions` directly from a page component.
- **`subAssociations.ts`** — currently **exactly one** real sub-association: `sa-tv` (Chi hội sinh viên Trà Vinh). There used to be two fictional ones (`sa-cntt`, `sa-kt`) from an earlier placeholder-data phase; those are gone. The live list now lives in `AppDataContext`'s `subAssociations` state (seeded from this file) since Admin can create new ones at runtime — pages should read `useAppData().subAssociations`, not import this file directly, except for the initial seed.
- **`users.ts`** — 15 real people (from `business_data/users.md`) plus one synthetic `u-admin` account. IDs `u-bch-1`, `u-bch-cntt-2`, `u-bch-cntt-3`, `u-member-1` through `u-member-5` are historical IDs kept stable because `activities.ts`/`posts.ts`/`badges.ts` reference them by ID — **don't rename these IDs without grepping for all references first.**
- **`activities.ts`** — **real events** (from `business_data/events/`), not mock/fictional ones. See the dedicated section below — this is the most critical real data in the system per the stakeholder.
- **`media.ts`** — the `Media` registry: real event photos (`img-<event>-<n>`, imported from `src/assets/events/`) and invented placeholder BCH-only documents (`doc-<event>-<n>`), keyed by id. Replaces the old `eventImages.ts` (deleted). `registerDocumentMedia()` lets `ActivityForm` register a newly mock-attached document at submit time so `getMediaById` can resolve it later.
- **`posts.ts`** — the unified `Post[]` seed (forum posts + feedback), replacing the old separate `forumPosts.ts` / `feedback.ts` (both deleted). Still mock/illustrative content, scoped to `sa-tv`.
- **`goals.ts`** — seed `Goal[]` — 2 invented placeholder goals (no real chỉ tiêu numbers supplied yet) distributing the 3 real activities across them, purely to exercise the assign-activity-to-goal feature.
- **`badges.ts`, `funds.ts`** — still mock/illustrative content, scoped to `sa-tv`. `funds.ts`'s expense entries reference the real activity IDs from `activities.ts` (amounts themselves are invented, not real). `funds.ts` no longer exports `QuotaInfo`/`quotaInfos` — that moved to `goals.ts`'s `Goal` shape.

## Permission system (added — see Session history #11)

Per the spec's "Cách vận hành" (operating mechanics) section: Permission is a fixed, developer-coded system concept (23 values in `types.ts`'s `Permission` union); Role→Permission is an **admin-editable mapping**, not hardcoded per role in components.

- **`AppDataContext`'s `rolePermissions: Record<Role, Permission[]>`** is the live, session-mutable source of truth, seeded from `permissions.ts`'s `defaultRolePermissions`. `togglePermission(role, permission)` flips one entry.
- **`context/usePermission.ts`** — `usePermission(permission)` (single check) and `useHasAnyPermission(permissions[])` are the only places a component should check access. They read `currentUser.role` against `rolePermissions`. **Don't inline `currentUser.role === 'bch'` for a feature gate** — that bypasses the admin-editable mapping. (Role-based checks are still fine for pure *display* branching that isn't a permission, e.g. Dashboard's per-role layout, or a badge's color tone — see `roleLabels.ts` and existing `role === 'bch'` display-only spots for the distinction.)
- **`RoleGuard`** now accepts either `permission={...}` (preferred — checked against `rolePermissions`) or `allow={[...]}` (role list — reserved for routes that are inherently role-specific rather than feature-gated, currently only `/admin`). Both can be combined; either failing redirects to `/403`.
- **`navConfig.ts`'s `getNavSections(role, grantedPermissions)`** filters the nav tree by permission, dropping empty groups — nav items carry an optional `permission` field instead of being hardcoded per role.
- **Admin page (`pages/Admin/Admin.tsx`)** is no longer a placeholder — it has three real sections per the spec: create a chi hội, assign a role to any existing user (account creation itself stays unsupported, per spec — "không hỗ trợ tạo tài khoản"), and a permission-matrix table (rows = permissions, columns = `bch`/`member`, checkboxes call `togglePermission`) that live-edits `rolePermissions`. `admin`'s own permission set is fixed/minimal and not shown as editable columns (only `bch`/`member` are, since admin's access is role-gated via `RoleGuard allow={['admin']}`, not permission-gated).
- Toggling a permission in Admin takes effect immediately across the app for that role (verified: turning off BCH's "Kiểm duyệt bài viết" makes "Kiểm duyệt diễn đàn" disappear from a BCH user's sidebar without re-login) — this is `AppDataContext` state, so it resets on page reload like everything else in the prototype.

## Real events (critical data — read before touching Activities)

Events/activities are, per the stakeholder, **the most critical data in this system**. Unlike everything else in `mock-data/`, `activities.ts` currently holds **real** events, not fictional placeholders:

- `act-hoi-thao` — Hội thao truyền thống Liên chi hội sinh viên Vĩnh Long lần thứ I – năm 2026 (17/8/2026, 8 real photos)
- `act-lao-dong-hk3` — Lao động học kỳ III – năm học 2025 – 2026 (22/7/2026, 5 real photos)
- `act-gop-nang-cho-em` — Hoạt động Góp nắng cho em – năm 2026 (18/7/2026, 7 real photos)

**Image rendering:** `Activity.mediaIds` mixes two kinds of ids that look the same (both plain strings) but resolve differently:
- `img-<event>-<n>` → a **real photo**, resolved via `mock-data/media.ts`'s `mediaLibrary` map (statically imported from `src/assets/events/<slug>/*.jpg`, so Vite bundles and hashes them).
- `placeholder-<n>` → the original **gradient placeholder tile** (`components/ImagePicker/placeholderStyle`), still used by `ActivityForm`'s image picker for newly created mock activities (there's no real photo-upload flow, so new activities can only use placeholders). These are intentionally *not* registered in `media.ts`'s registry — `ActivityImage` falls back to the gradient renderer for any id `isRealImage()` doesn't recognize.

**Always render activity images through `components/ActivityImage/ActivityImage.tsx`** — it checks `isRealImage()` and renders an `<img>` for real photos or the gradient `<div>` for placeholders, so callers (`ActivitiesList`, `ActivityDetail`) don't need to know which kind they have. Don't call `placeholderStyle()` directly on an id that might be a real photo id.

**BCH-only documents still apply to real events.** No real documents were supplied for these events, so each one carries 1–2 **invented placeholder document names** (e.g. `Ke-hoach-gop-nang-cho-em.docx`, now `Media` entries with `kind: 'document'` in `media.ts`) purely to exercise the existing BCH-only visibility feature (§3.2 of the spec) — `ActivityDetail.tsx` now gates this section on `usePermission('manage-activities')` rather than a raw role check, verified working: a member account sees the photos/description/participants/benefits but not the "Chỉ BCH mới xem được mục này" banner or any document names. **If real documents are supplied later, replace these placeholder names — don't just add to them.**

**Also invented, same caveat:** each real activity now carries 2–3 placeholder `benefits` entries (e.g. "Điểm rèn luyện", "Đạt tiêu chí Tình nguyện tốt của danh hiệu Sinh viên 5 tốt") — no real benefits list was supplied. Replace, don't append, if real data arrives.

## Pages and routing

Routes are defined in `App.tsx`, wrapped in `AppShell` (header + sidebar nav) once logged in, gated per-route by `RoleGuard` (`permission={...}` preferred, `allow={[...]}` roles for `/admin` only — see "Permission system" above).

**Sidebar structure** (`components/AppShell/navConfig.ts`, `getNavSections(role, grantedPermissions)`): flat member items (Bảng tin, Hoạt động, Diễn đàn, Góp ý & phản hồi, Thông tin chi hội) for everyone, then — for `bch` only — a divider and an always-expanded "Công tác hội" section (Hội viên, Huy hiệu, Kiểm duyệt diễn đàn) containing a nested always-expanded "Tiện ích" sub-section (Chỉ tiêu, Quỹ chi hội, Tạo bản in). `admin` gets its own minimal flat list (Bảng tin, Quản trị hệ thống). Each item is additionally filtered by the current role's live `rolePermissions` — an item disappears if the role loses the permission it declares, even without a code change. **"Hồ sơ cá nhân" is intentionally not in the sidebar** — it's reached via the account dropdown in the header (`AppShell.tsx`'s `accountMenu`), for both member and bch roles. If you add a nav item, decide deliberately whether it belongs in the flat list, the "Công tác hội" group, or "Tiện ích" — don't just tack it onto the top level, that's the clutter this structure was built to avoid.

Full page-by-page intent is documented in `docs/prototype-specification.md` §5 — that document does not need to be re-derived, just kept in sync if a page's purpose changes materially.

Quick reference of what's built (all present, matching the plan):

- Login (mock account picker) → Dashboard (role-aware) → Profile (editable, display-only fields) → Sub-Association Info → Activities (list/detail/create/edit, now with benefits) → Members (sortable list/detail) → Badges (create/assign/remove/**delete**) → Feedback (unified Post, `postType: 'feedback'`) → Forum (list/detail/create/moderation, unified Post, `postType: 'forum'`) → Quota (Goal-based, assign-activity modal) → Funds → Documents (mock export) → Admin (chi-hội creation + role assignment + permission matrix) → 403/404.

## Key architectural decisions worth knowing before you change things

1. **`getUserRoleLabel()` is the only place role labels are computed.** If you add a new place that displays a user's role, call this helper — don't inline a `role === 'bch' ? 'BCH' : ...` ternary or a local `ROLE_LABELS` map. Two such local maps existed in earlier code (`Login.tsx`, `AppShell.tsx`) and had to be found and removed when titles were introduced.
2. **`AppDataContext` is the single mutable data store for the session.** All CRUD-ish interactions (create/edit/delete activity, assign/remove/delete badge, post/comment, feedback status, core-member toggle, goal creation/activity-assignment, sub-association creation, user role assignment, permission toggling) go through it, not through local component state or direct mock-data mutation. Mock-data files are only ever used as the *seed* passed into `useState` inside the provider.
3. **IDs matter for cross-references.** Activities/badges/posts reference users and each other by string ID. When adding/removing mock users, check `activities.ts`, `posts.ts`, `funds.ts`, `goals.ts` for dangling references.
4. **Destructive actions get a confirm step, not a native `confirm()` dialog.** Badge deletion (`Badges.tsx`) uses a two-step button state inside the existing `Modal` footer instead of `window.confirm`, because native dialogs block the Claude-in-Chrome browser automation tools used to verify changes in this project. Follow this pattern for any future destructive action.
5. **Vite is pinned to v6, not the installed-by-default v8.** See the Tech stack table above — don't `npm update` vite without checking the Node engine requirement first.
6. **`ActivityImage` is the only place that decides real-photo-vs-placeholder rendering.** See "Real events" above — don't reintroduce a direct `placeholderStyle()` call on activity image ids.
7. **`usePermission()` is the only place a feature-level access check should go.** See "Permission system" above — don't inline `currentUser.role === 'bch'` for gating a feature/section; that silently bypasses Admin's permission matrix. Pure display branching (not a feature gate) is still fine to check by role directly.
8. **`activeSubAssociationId` (from `AuthContext`), not `currentUser.subAssociationIds[0]`, is what chi-hội-scoped pages should read.** It's set on login and is the "currently viewing chi hội" concept for a multi-membership user; reading the raw array's first element in a new page would silently ignore that indirection if it's ever wired up to a switcher UI later.

## Verifying changes

This project is checked visually via the `claude-in-chrome` skill (a real Chrome browser automated via CDP), not just by reading code. Workflow used so far:

1. Make the change.
2. `npx tsc -b` (or `npm run build`) to catch type errors — the dev server's HMR is more lenient and will hide real bugs (this has happened before — see Session history).
3. Start/confirm the dev server is running (`npm run dev`, default port 5173; check for orphaned duplicate dev-server processes on other ports before starting a new one).
4. Use `claude-in-chrome` to navigate, click through the affected flow, and screenshot it.
5. **Known flakiness:** on this Windows/Chrome setup, `computer` tool's synthetic clicks on some `<button>`/`<a>` elements intermittently fail to trigger React's event handlers (no console errors, just no navigation), and `Page.captureScreenshot` intermittently times out on the first attempt after an action. Neither indicates an app bug by itself. Workarounds that have worked: retry the screenshot once; if a click genuinely isn't registering, dispatch it via `javascript_tool` (`element.click()` in page context) instead of the coordinate/ref-based `computer` click, and use `get_page_text` to confirm navigation succeeded when screenshots are being uncooperative.
6. Because auth state is React-context-only, **any full navigation (typed URL, `navigate` tool, page refresh) logs the session out back to `/login`.** Only client-side link/button clicks preserve the session. This is expected — don't chase it as a bug.
